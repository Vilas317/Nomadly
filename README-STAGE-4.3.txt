ENVIRONMENT
-----------
Set GOOGLE_CLIENT_ID in the API environment file loaded by apps/api.
Set NEXT_PUBLIC_GOOGLE_CLIENT_ID in apps/web/.env.local.
Both must be the SAME Google OAuth 2.0 Client ID of type Web application.

Never put a Google client secret in NEXT_PUBLIC_* variables. This ID-token
credential flow does not require a client secret.

Google Cloud Console local setup:
- Authorized JavaScript origin: http://localhost:3000
- Add your production origin before deploying.

DATABASE / MIGRATION
--------------------
The schema adds OAuthProvider and OAuthAccount. The migration creates the enum,
table, unique provider-subject constraint, unique user/provider constraint,
and user foreign key.

Before applying, check migration status:

  pnpm --filter @nomadly/api exec prisma migrate status

Then apply the checked-in migration using your existing migration workflow:

Do not run `migrate dev --name ...` as well; the migration SQL is already supplied.
If `migrate status` reports a failed or divergent migration, stop and resolve that

SECURITY / ACCOUNT BEHAVIOUR
----------------------------
- Google ID token signature, issuer, audience and expiry are verified with
  Google's maintained google-auth-library.
- A verified Google email is required.
- Google `sub` is persisted as the stable provider identity.
- Returning Google users are resolved by provider + subject, not email.
- A new verified Google identity can link to an existing Nomadly account with
  the same verified email.
- A Google email change does not strand an already-linked account: the stable
  Google subject remains authoritative and only providerEmail metadata updates.
  The Nomadly account email itself is not silently changed.
- New Google accounts get a random unusable password hash and a verified email.
- Existing accounts without a Profile or inactive accounts are rejected.
- Existing controller creates the normal Nomadly AuthSession and HttpOnly cookies.

TESTS
-----
Do not repeat the already-passed Stage 4.2 tests. After builds and migration,
perform focused Google checks:
1. Invalid credential is rejected and creates no user/OAuthAccount.
2. First successful Google sign-in creates one OAuthAccount and one AuthSession.
3. Repeated sign-in reuses the same User/OAuthAccount and creates a fresh session.
4. If the Google email matches the existing verified password account, it links
   to that same User (no duplicate User).
5. Revoking the Google-created session invalidates its access token.

Do not commit or push until migration status, builds, and focused checks pass.
